# Gefjon v0.2 设计方案：单一二进制 + 多生态迁移后端

> 状态：**设计稿（待评审）**。本文只描述方案，不代表已实施。
> 目标读者：维护者与使用方。

---

## 1. 背景与目标

v0.1 是一个 Python 包（`pip install gefjon`）。它工作正常，但**不适合直接嵌进别人的项目**：

| 维度 | v0.1 现状 |
| :--- | :--- |
| 分发形态 | Python 包，使用方必须有 Python 环境 |
| 依赖净体积 | **49.8 MB**（SQLAlchemy 18.0 / cryptography 10.6 / pygments 8.4 / rich 2.8 / pydantic 3.8 …），不含 CPython 运行时 |
| 打包成单文件 | PyInstaller 预计 **70–90 MB**，与"精致小巧"直接冲突 |
| 资源文件 | 模板与脚手架从包数据读取（v0.1 就发生过 `alembic.ini.template` 漏打包的故障） |

**v0.2 目标**：

1. **单一静态二进制**，下载即用，目标机器无需 Python；
2. **可内嵌**：放进项目/CI 直接调用，或作为库被 Go 程序引入；
3. **小**：核心二进制目标 **< 6 MB**（linux/amd64，stripped）；
4. **`models.yaml` 是唯一权威**：同一个 schema 定义可产出多个生态的迁移工程；
5. **零 Python 依赖**，且不把任何数据库驱动塞进核心二进制。

---

## 2. 设计原则（本方案的立足点）

### 2.1 为什么不能"把 Alembic 内嵌进二进制"

实测（v0.1 产物）：

```
迁移脚本 = Python 代码：from alembic import op + 8 处 op.create_table(...)
alembic_version = VARCHAR(32) NOT NULL 单列表
```

- Alembic 是 Python 库，**迁移脚本本身是可执行的 Python 代码**，Go 无法执行；
- 唯一办法是内嵌 CPython：需要 CGO + 目标平台的 `libpython`，破坏 `CGO_ENABLED=0` 静态单文件，交叉编译几乎不可行，体积回到 50–90 MB（且当前环境没有 gcc，CGO 直接不可用）；
- 但 `alembic_version` 格式极简，**Go 完全可以读写它** —— 所以"版本接力"没有问题。

### 2.2 Gefjon **不连数据库**

这是让二进制变小、让设计变干净的关键：

| 职责 | 归属 |
| :--- | :--- |
| 解析与校验 `models.yaml` | **Gefjon**（纯文本处理，零数据库依赖） |
| 编译成各生态的 schema 产物 | **Gefjon** |
| 连库、算 diff、执行迁移、维护版本表 | **目标生态的原生工具**（Atlas / Alembic / Flyway） |

因此核心二进制**不含任何数据库驱动**，也不需要网络。

### 2.3 执行权交给生态原生工具

`models.yaml` 是绝对权威，各生态只是它的"编译目标"：

| 技术栈 | 推荐后端 | 执行工具 |
| :--- | :--- | :--- |
| Python | `alembic` | alembic（Python） |
| Go | `atlas` | atlas（**单个 Go 二进制，可自动获取**） |
| Java | `flyway` | flyway |
| 其它 / 只想拿 SQL | `plain-sql` | 任意（也可用 atlas 执行） |

## 3. 架构

```
cmd/gefjon/main.go            # CLI 入口
internal/
  config/                     # models.yaml 解析 + 校验（对齐 v0.1 的白名单/受限解析规则）
  types/                      # 类型目录（PostgreSQL / MySQL / SQLite）
  model/                      # 归一化后的 schema 中间表示（IR）
  render/                     # 模板渲染（原子写、先渲染后落盘、确定性输出）
  backend/                    # 后端接口 + 各实现
    alembic/  atlas/  flyway/  plainsql/
  toolchain/                  # 外部工具的探测、版本校验、按需获取（含 SHA256 校验）
  state/                      # .gefjon/state.json（targets、last revision、baseline）
  cli/                        # 命令装配、交互式向导
internal/templates/           # go:embed 打进二进制（不再依赖任何外部文件）
third_party/                  # 许可证与来源记录
```

**中间表示（IR）**：`models.yaml` 先编译成与后端无关的 IR（表、列、类型、索引、约束、关系），各后端只负责 IR → 目标产物。这样新增一个生态只需实现一个 backend，不必动解析层。

## 4. `models.yaml` 的扩展

保留 v0.1 的全部字段（**契约不变**，可直接迁移），新增 `targets`：

```yaml
project:
  name: myproject
  version: 1.0.0

database:
  dialect: postgresql        # postgresql | mysql | sqlite

models:
  - name: User
    # …与 v0.1 完全一致…

targets:                     # 新增：要把这份 schema 编译成哪些生态的产物
  - kind: atlas              # Go 服务用
    dir: db/migrations
  - kind: alembic            # Python 作业用
    dir: migrations
  - kind: flyway             # Java 服务用
    dir: src/main/resources/db/migration
```

- 不写 `targets` 时，按 v0.1 的 `migration:` 段推断出单个 `alembic` target（**向后兼容**）；
- 一个项目可以同时声明多个 target（这就是"双轨"的另一种形态：**同一权威，多份产物**）。

## 5. 后端能力矩阵

| kind | 生成产物 | 执行工具 | 版本表 |
| :--- | :--- | :--- | :--- |
| `alembic` | `models/*.py`、`migrations/env.py`、`migrations/script.py.mako`、`migrations/versions/*.py` | `alembic`（Python，需环境） | `alembic_version` |
| `atlas` | `schema.hcl`、`atlas.hcl`、`migrations/*.sql` | `atlas`（单二进制，可自动获取） | `atlas_schema_revisions` |
| `flyway` | `V<version>__<desc>.sql` | `flyway`（Java，需环境） | `flyway_schema_history` |
| `plain-sql` | `<timestamp>_<desc>.sql`（up/down） | 任意工具 | 由使用者决定 |

**共同约定**：迁移内容一律来自 IR；Gefjon 只生成文件，不连库。

## 6. 交互式 `init` 与"自动推荐"

`gefjon init` 无参数时进入向导，**探测项目技术栈后推荐最优配置**：

| 探测到 | 推荐 target | 说明 |
| :--- | :--- | :--- |
| `go.mod` | `atlas` | 执行工具是单二进制，最能保持"零环境依赖" |
| `pyproject.toml` / `requirements.txt` | `alembic` | 与现有 v0.1 用户一致 |
| `pom.xml` / `build.gradle` | `flyway` | Java 生态原生化 |
| `package.json` | `plain-sql` | Node 生态暂无标准迁移工具，先出 SQL |
| 都没探到 | 询问 + 默认 `plain-sql` | |

向导会：
1. 探测技术栈与 `database.dialect`；
2. 展示推荐项与**理由**（"检测到 go.mod → 建议 atlas：单二进制，无需额外环境"）；
3. 允许 `--yes` 跳过交互（CI 场景）；
4. 生成 `models.yaml` 骨架、`.gefjon/state.json` 与所选后端的最小脚手架。

## 7. 工具按需获取（"网络加载依赖"）与安全

核心二进制**不自带** atlas / alembic / flyway。执行类命令按需获取：

```
gefjon doctor                    # 诊断：每个 target 需要的工具是否可用、版本是否符合
gefjon tool install atlas        # 下载到 ~/.cache/gefjon/tools/atlas/<version>/
gefjon migrate --message "…"     # 缺工具时提示，而不是静默下载
```

**安全约束（硬性）**：

1. 内置**工具清单**：名称 → 固定版本 → 官方下载 URL → **SHA256**。校验和不匹配即拒绝使用；
2. **默认不自动下载**：执行前只提示；`gefjon tool install` 或显式 `--allow-download` 才联网；
3. 可配置镜像源，但**镜像也必须通过同一份 SHA256 校验**；
4. 下载产物落在用户缓存目录，权限收紧；不写入项目目录；
5. `gefjon doctor --offline` 可在无网环境自查。

> 理由：自动联网下载可执行文件是典型的供应链攻击面。宁可多一步显式确认。

## 8. 产物与状态

```
<project>/
├── models.yaml                 # 唯一权威
├── .gefjon/state.json          # targets、各后端 last revision、baseline 记录
└── <各 target 的目录>/          # 由 target 决定
```

`.gefjon/state.json` 记录：

```json
{
  "schema_version": 1,
  "targets": [
    {"kind": "atlas", "dir": "db/migrations", "last_revision": "20261016_add_user"}
  ],
  "baselines": [
    {"target": "atlas", "adopted_from": "alembic_version", "revision": "ab12cd34", "at": "…"}
  ]
}
```

生成产物仍是**确定性**的（不含时间戳），`gefjon generate --check` 继续作为 CI 漂移检测。

## 9. 历史 Alembic 项目的交接（baseline 接力）

已有 `alembic_version` 的项目切到新后端时：

1. `gefjon migrate --adopt` 读取现有 `alembic_version` 的值；
2. 在目标后端的版本表里写入一条 **baseline** 记录（表示"截至此 revision 的 schema 已存在"）；
3. **打印醒目警告**：历史 `*.py` 迁移不会再被执行，后续变更由新后端接管；
4. 同时把当前 schema 导出为快照（`schema.hcl` 或 `.sql`），作为新后端的比较基线。

原则：**不猜测、不静默转换**。历史 `*.py` 的自动转换（解析 `op.*` 调用）明确**不做** —— 易错且不可靠。

## 10. 体积与构建

- 构建：`CGO_ENABLED=0 go build -trimpath -ldflags="-s -w"`（静态、无外部依赖）；
- 模板与脚手架：`go:embed`，**运行时零外部文件**；
- 体积目标（linux/amd64）：

| 形态 | 预估 |
| :--- | :--- |
| 核心（解析 + 生成 + 编排，无驱动） | **4–6 MB** |
| 可选构建标签（内置 SQLite 驱动等） | +8–12 MB |

- 发布：GitHub Actions 矩阵交叉编译 `{linux,darwin,windows} × {amd64,arm64}`，附 SHA256 与 SBOM；可选 Homebrew / Scoop / `install.sh`。

## 11. 里程碑

| 阶段 | 内容 | 验收 |
| :--- | :--- | :--- |
| **M1** | Go 骨架、`models.yaml` 解析/校验（对齐 v0.1 白名单与受限解析）、IR、`generate` + `--check`、embed 模板 | 与 v0.1 生成的模型代码**逐字节一致**（golden fixtures） |
| **M2** | 交互式 `init`、技术栈探测与推荐、`.gefjon/state.json` | 在 Go/Python/Java 三种样例项目上给出预期推荐 |
| **M3** | `alembic` 后端（env.py / script.py.mako / versions） | 与 v0.1 产物逐字节一致 |
| **M4** | `atlas` 后端（HCL + SQL）、工具清单与 `tool install`（SHA256 校验） | 校验和不匹配时拒绝；离线可用 |
| **M5** | `flyway` 后端、`plain-sql` 后端、`doctor`、baseline 接力 | 四种后端在同一份 `models.yaml` 上各自产出可用工程 |
| **M6** | 跨平台发布流水线、安装脚本、迁移指南（v0.1 → v0.2） | 三个平台下载即用 |

**关键做法**：在删除 Python 实现**之前**，先用它把产物固化成 golden fixtures（现有 240 项测试是现成的行为规格），Go 版逐一对齐后才移除 —— 这是"完全取代"的安全路径。

---

## 12. 风险与对策

| 风险 | 对策 |
| :--- | :--- |
| 行为对齐成本（3643 行 Python + 240 项测试） | 先用 golden fixtures 锁定产物；分阶段替换；每阶段可回退 |
| Atlas / Flyway 的版本表语义与 `alembic_version` 不同 | baseline 接力显式化 + 警告；绝不做隐式转换 |
| 按需下载工具 = 供应链面 | 固定版本 + SHA256 + 默认不自动下载 + 可离线 |
| 多后端 × 多数据库的测试矩阵膨胀 | 用容器化的 PG/MySQL 做集成测试（v0.1 的 CI 已具备雏形） |
| 多语言产物的"权威性"漂移 | 始终以 `models.yaml` 为唯一输入；产物只读、由 CI 的 `--check` 校验 |
